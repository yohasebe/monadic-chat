# 共有フォルダとサーバーのコード

共有フォルダ（`~/monadic/data`、コンテナ内では `/monadic/data`）には、モデルが実行するコードから書き込めます。Code Interpreter などのツールは、共有フォルダを読み書きできる形でマウントした Python コンテナでコードを実行し、モデルへの入力は、読んだもの（文書や Web ページ）で誘導されえます。一方、Ruby のサーバーは API キー（自身の環境、`/monadic/config/env`、1Password から届けた `/run/monadic-secrets/env` の値）を読め、コンテナでは Docker のソケットも使えます。そのため、モデルが書けるものが、サーバーの実行するコードになってはいけません。

## サーバーが実行・読み込むもの

- **Ruby 側のコマンド**（`send_command(container: "ruby")`）：PATH には、同梱のスクリプトのフォルダと、サーバー自身の PATH のうち、絶対パスで、存在し、実体が共有フォルダの外にあるものだけを置きます。同梱の Ruby スクリプト（`tts_query.rb ...`）は `RbConfig.ruby` と絶対パスで起動し、同梱でない Ruby スクリプトは拒否します。実行権は付けません。コマンドの環境からは認証情報（`*API_KEY`・`*_KEY`・`*TOKEN`・`*SECRET`・`*PASSWORD`・`*CREDENTIALS`）を外します。同梱のスクリプトは設定から鍵を読みます（`SecretReferences.config_value`）。共有フォルダの `scripts` の利用者スクリプトは、Python コンテナでだけ実行されます。
- **自作のアプリとヘルパー**（`apps/`・`helpers/`）：`SharedPathGuard.user_code_files` と `code_files` を通して読み込みます。フォルダ自体がリンクなら何も読まず、リンクのファイル、別のハードリンクがあるファイル、実体がフォルダの外にあるファイルも読みません。DSL のローダーは、アプリの `_constants.rb`・`_tools.rb` も同じ規則（`code_file?`）で読み込みます。
- **コンテナの定義**（`services/`・`apps/*/services/`）：`monadic.sh` は、その `compose.yml` をすべての `docker compose` の実行に含め、「Build User Containers」でビルドします。生成する include のファイルは、共有フォルダではなく `~/monadic/config` に書きます。
- **ホストが共有フォルダで読み書きするほかのもの：** Electron アプリは、ドキュメント DB の書き出しと、復号した取り込み用のファイルを、`~/monadic/.staging`（共有フォルダの隣で、どのコンテナもマウントしない）に新しく作ったファイルに書き、エラーなく書き終えて閉じたときだけ、名前を付け替えて置きます（付け替えはリンクや FIFO をたどらず置き換えます）。読むときは、確かめた通常のファイルだけを、止まらずに開きます（`app/no_follow_files.js`）。置いた後のファイルは、ほかの共有フォルダのファイルと同じで、`import_db` が読むまでの間に変えられえます。開くのは共有フォルダそのものだけで、ほかのフォルダは親フォルダの中で選択して見せます。そこにあるフォルダはアプリ（macOS の `Name.app`）でありえ、開くと実行されるためです。
- **Python コンテナの PATH：** 利用者の `scripts/` はシステムのものより後ろに置きます。そこに置かれた `python3` や `bash` が本物の代わりになることはありません。

## 境界を守る場所

- **コンテナ（デスクトップアプリ）：** 共有フォルダをマウントするすべてのコンテナ（Python・Selenium・Extractor、そして読むだけの Ruby も）で、`apps/`・`helpers/`・`services/` を読み取り専用で重ねてマウントします。このマウントを通る書き込みは、どんな経路（リンク、確認と書き込みの間の差し替え）でもファイルシステムが拒否し、そこへ新しいハードリンクを作ることもできません（マウントをまたぐリンクや、読み取り専用の場所へのリンクは拒否されます）。ただし、マウントより前から別の名前のハードリンクがあったファイルは、その名前からなら書けます。サーバーはリンクが 2 つ以上あるファイルを読み込みません（`SharedPathGuard.code_file?`）が、その名前から書き換えた後、次の起動までにその名前を消されると見分けられません。そうした古いリンクは、フォルダを点検する（リリースノートを参照）か、コードを共有フォルダの外へ移すことでしか除けません。`monadic.sh`（`ensure_code_dirs`）は、どのコンテナよりも先に 3 つのフォルダを利用者の権限で作り、作れないときやリンクのときは起動しません（コンテナを下ろす操作は、復旧の手段として動きます）。
- **サーバーが共有フォルダに書くもの：** ファイル名をモデルやページが決める書き込み（ファイルのツール、アップロード、Web 検索の保存、プロバイダが送るファイル、アプリのテンプレート、AutoForge のプロジェクトのファイル）は `SharedPathGuard.write_file!` で書きます。`apps`・`helpers`・`scripts`・`services` には（名前を大文字小文字の区別なく、また実体の場所でも）書かず、書く場所がリンクなら（解決の前後とも）拒否し、`File::NOFOLLOW` で開きます。名前をサーバーが作る書き込み（生成した画像・音声・文字起こし）と、AutoForge のパッチの適用・復元は通りません。コンテナでは読み取り専用のマウントがそれらも守ります。コンテナでは二重の守りで、ホストでは唯一の守りです。

## 開発モード

`rake server:debug` ではサーバーがホストで動きます。ほかのコンテナでは `apps/`・`helpers/` は読み取り専用のままなので、モデルが実行するコードは、そこへ直接書くことも、新しいハードリンクを作ることもできません。ただしホストのサーバーは渡されたパスをたどります。`write_file!` は書く場所のリンクを拒否しますが、確かめてから開くまでの間に親フォルダをリンクに差し替えられると、別の場所へ書くことになります（`File::NOFOLLOW` が効くのはパスの最後の部分だけ）。

そのため開発モードでは、シェルで `MONADIC_LOAD_USER_CODE=true` を付けて起動しない限り、サーバーは共有フォルダの自作アプリとヘルパーを読み込みません（`SharedPathGuard.user_code_files`）。

```bash
MONADIC_LOAD_USER_CODE=true rake server:debug
```

有効にできるのはシェルだけです。`rake server:debug` は、サーバーの起動前に `~/monadic/config/env` を `ENV` に入れますが、この設定はシェルにあったときだけサーバーへ渡します。さらにサーバーは、このファイルのどこかにこの名前があれば無効として扱います（バイト列を探すだけで、解析も表示もしません。アカウントの home と `HOME` の両方のファイルを見ます）。Dotenv は、行ごとの解析では見落とす書き方（`NAME: value`、BOM、CR だけの改行）も受け付けるためです。コンテナの中かどうかは `IN_CONTAINER` ではなく `/.dockerenv` で判断します。無効のときにフォルダにファイルがあれば、起動時に一度だけ知らせます。自作アプリを作っている間だけ付け、信頼できない文書やページをモデルに読ませるときは付けないでください。
