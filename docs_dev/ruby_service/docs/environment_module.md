# Environment Module

`Monadic::Utils::Environment` (`lib/monadic/utils/environment.rb`) detects whether the Ruby code runs in the Ruby container or on the host (development mode) and resolves paths for both.

## Detection

`in_container?` returns, in order: `ENV["IN_CONTAINER"] == "true"` when the variable is set, the `IN_CONTAINER` constant when defined, otherwise whether `/.dockerenv` exists.

## Paths

`resolve_path(container_path, local_path = nil)` returns `container_path` in the container; on the host it returns `local_path`, or `container_path` with `/monadic` replaced by `~/monadic`.

| Method | Container | Host |
|---|---|---|
| `config_path` | `/monadic/config` | `~/monadic/config` |
| `env_path` | `/monadic/config/env` | `~/monadic/config/env` |
| `data_path`, `shared_volume` | `/monadic/data` | `~/monadic/data` |
| `state_path` | `/monadic/state` | `~/monadic/state` |
| `scripts_path`, `apps_path`, `helpers_path` | `data_path` + `scripts`, `apps`, `helpers` | same, under `~/monadic/data` |
| `log_path` | `/monadic/log` | `~/monadic/log` |
| `command_log_file`, `extra_log_file`, `jupyter_log_file` | `command.log`, `extra.log`, `jupyter.log` in `log_path` | same |
| `system_script_dir` | `/monadic/scripts` | `docker/services/ruby/scripts` in the source tree |

The config env file is read through `Monadic::Utils::EnvFile` (`lib/monadic/utils/env_file.rb`), by the server (`lib/monadic.rb`, for both ENV and CONFIG), `rake server:debug`, the test runner and the help build script; nothing else loads it into the environment (a spec checks there is no `Dotenv.load`/`parse` elsewhere). It parses the file itself: `KEY=value` lines, optional `export`, plain, single-quoted or double-quoted values; nothing is expanded or run (`${VAR}` and `$(...)` stay text). Only the settings the code reads from ENV go there (`ENV_KEYS`, `*_API_KEY`, `*_DEFAULT_MODEL`; `spec/unit/utils/env_file_spec.rb` checks the list against the code), and a value the shell set is kept. Settings that decide where requests go or what program runs (`REFUSED`: proxies, `QDRANT_URL`, `EXTRACTOR_URL`, `EMBEDDINGS_URL`, `MONADIC_OP_CLI`, ...) are not taken for ENV or CONFIG, nor are names of that form (`REFUSED_PATTERNS`: ending in `_URL`, `_HOST`, `_ENDPOINT`, `_PROXY`, `_SOCKET`, `_CMD`, `_COMMAND`, `_BIN`, ..., or in `_PATH`, `_DIR`, `_FILE` unless the key is in `PATH_KEYS`), so a setting added later needs a check in `EnvFile` before the file can set it (a spec checks that no key the code reads from CONFIG by name is lost this way); a port (`PORT_KEYS`) must be a number from 1 to 65535; a setting that names a file (`PATH_KEYS`) must be an absolute path to an existing file or folder outside the shared folder, and is passed on as its real path. The names of settings left out are printed (never values).

`state_path` holds server-owned records outside the shared folder. It is mounted into the Ruby container only. One server writes it: at start the server takes a numbered mark in `server.owner/` (`Workspace::ServerOwner`) before reading the ledger, and does not start when another server holds it. A mark left by a server that stopped is followed only when that server is known to have stopped (another start of the container, or its process gone; from the host, Docker answering that the Ruby container has stopped). Ledger changes run inside `ServerOwner.writing`, and a stopping server lets them finish before it notes in its mark that it has stopped. The ledger (`ledger.json`) is checked on every read and before every save (`Workspace::LedgerSchema`: ids of each kind, chats and workspaces that point at each other, attachment paths inside their chat's folder, size and sha256 on a ready attachment); a ledger that is not JSON, not of that form, or written by a newer version raises `Ledger::Syntax`, `Shape` or `Newer` (all `Ledger::Unreadable`), and a change that would leave it out of form is not saved. Fields and collections it does not know are kept. The ledger is version 2 (`artifacts` and `publications` added). A version 1 ledger (beta.42, beta.43) is read in the version 2 form without being changed; the first change keeps its bytes as they were in `ledger.json.v1.bak` (an existing backup of other bytes is left, and these go under another name), settled on disk with its folder before the ledger is replaced, and then saves version 2 (`Ledger::NotUpgraded` and nothing changed when the backup fails). Every save settles the folder after the replacement (a folder that cannot be synced is not taken as synced); when that fails, the process writes no more to that ledger, under any path that names it (`Ledger::Unsettled`), until the server starts again, and an attachment whose ready record was put in place this way keeps its file. Nothing is put back automatically: going back to the backup loses what was recorded since, and a version 1 server refuses a version 2 ledger. Before the first start of version 2, servers of an earlier version (in the container or run from the host) must be stopped: they do not know `ServerOwner`.

What a run makes (today the WebVTT and SRT subtitles of a timed transcript) is kept as an artifact in `state_path/artifacts/<artifact id>/` (`Workspace::Artifacts.store!`), where only the server writes, and recorded in the ledger with the size and sha256 of the bytes the server wrote. A run (`Workspace::Jobs`) belongs to the chat the ledger gives for its workspace (`Jobs.create!(workspace_id)`) or, for runs asked for from outside any chat (the MCP server), to a folder set aside for them (`LedgerSchema::OUTSIDE_ROOTS`); the artifact records that owner, the job, its kind and `copy_path`, the place of the copy written in the run folder for people and other programs to read. `copy_path` only says where a copy was written: more than one record can name the same path, and a record is never found by it. Nothing trusts that copy: subtitles are published from the kept artifact, and subtitles that could not be kept are neither copied to the run folder nor published. No artifact is made while the ledger is no longer written or the server is stopping; a kept file is removed when its record cannot be made, and kept when the record may have been saved but not settled.

An image a chat's generator made (kind `image`, `Workbench::Artifact`) has no kept copy: the file in the chat's folder (`copy_path` = `<chat folder>/artifacts/<YYYYmmdd-HHMMSS>_<generator's name>.<ext>`) is the only one, and the user may move or delete it. The server checks the generator's bytes, writes them as a new file there (`SharedPathGuard.write_file!` with `replace: false`, `strict: true`, synced with its folder; a name already taken gets `-2`, `-3`, …) and then records it with its size, sha256, type, dimensions, the workbench run (`run`, recorded once: a run already recorded is not placed again) and request, and the image it was made from. All of this runs under the chat's workbench lock after its epoch and the reply's request are checked, so a Cancel or Reset comes before it (nothing is made) or after it. A file made and not recorded (the ledger failed, or the process stopped) stays as a file of the user's and is never taken up by its name. Every use (the work screen, an edit, a download) reads the file with no link on the way, at most the recorded size, and uses those bytes only when their sha256 is the recorded one (`Artifact::Changed`, `Artifact::Missing` otherwise), for the chat the server knows the caller is in. Images are not published.

What the page loads by a `pub_` name (an attached video, a chat's subtitles) is a publication (`Workspace::Publications`; the name is the code's: the copy is served only by the local server, which listens on loopback, to the app's own page): a copy in `state_path/publications/<publication id>/pub_<the random part of that id>.<ext>`, recorded in the ledger with its source (a ready attachment or artifact of a chat, with the source's sha256), its size, sha256 and type. The copy is made from the bytes read once from the source (an attachment through `SharedPathGuard`, never through a link; an artifact from the state folder) and hashed as they are written; it becomes ready only when those bytes have the size and sha256 the ledger recorded for the source, and after the copy and its folders are synced. A source has at most one publication pending or ready; pending, ready and revoked are checked again inside the ledger's lock, so a publication revoked while it was copied never becomes ready. A ready publication is used again while its copy is there with its size and sha256 (checked as before serving); one whose copy is gone or of other bytes is marked missing and a new one is made (a copy that cannot be read now is not taken for gone). No publication is made when the pending and ready copies would take more than 10 GB (counted inside the ledger's lock), or the disk would be left with less than 2 GB free (`df`, checked again before each copy: a process makes one copy at a time). Only a folder the call made is removed when it fails, and a pending record goes only once its folder is known to be gone; otherwise it stays pending and the next start removes both. Serving reads the ready publications from the ledger once per version of the ledger file (a save puts a new file in place). Runs outside any chat are not published. Every `/data/` and `/monadic/data/` name starting with `pub_`, in any case, is answered from the ledger alone: the ready publication with exactly that name, from its copy, while its chat's folder is there (checked from the shared folder with no link on the way, `SharedPathGuard.directory_stat`) and the copy's bytes have the recorded sha256 (hashed from the file that is served, and remembered while the copy keeps its file, size and times); anything else is 404, and no `pub_` file in the shared folder is ever served. At start, before requests are taken, publications left pending are removed, and those whose chat's folder is gone (not there at all; a folder that cannot be read is left alone) are revoked and their copies removed; nothing is removed when the ledger cannot be read. A chat folder renamed away with another folder of the same name put in its place is not told apart.

## Log Rotation

`rotate_log(file)` renames `file` to `file.1` (shifting older files up to `file.<max>`) once it exceeds `LOG_ROTATE_MAX_BYTES` (default 5 MB). `LOG_ROTATE_MAX_FILES` (default 5) sets the number of files. Errors are ignored.

## Usage

```ruby
Monadic::Utils::Environment.in_container?
Monadic::Utils::Environment.data_path
```

A class that includes the module also gets the methods as class methods.
