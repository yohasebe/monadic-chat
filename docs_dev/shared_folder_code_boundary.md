# Shared Folder and Server Code

The shared folder (`~/monadic/data`, `/monadic/data` in the containers) can be written by code a model runs: Code Interpreter and other tools run code in the Python container, which mounts the shared folder read-write, and the model's input can be steered by what it reads (a document, a web page). The Ruby server can read the API keys (its environment, `/monadic/config/env`, the values delivered from 1Password in `/run/monadic-secrets/env`) and, in the container, the Docker socket. Nothing a model can write may therefore become code the server runs.

## What the server runs and loads

- **Commands on the Ruby side** (`send_command(container: "ruby")`): PATH holds the bundled script folders and the absolute, existing folders of the server's own PATH whose real path is outside the shared folder. A bundled Ruby script (`tts_query.rb ...`) runs as `RbConfig.ruby` with its absolute path; a Ruby script that is not bundled is refused. Nothing is made executable. Credentials (`*API_KEY`, `*_KEY`, `*TOKEN`, `*SECRET`, `*PASSWORD`, `*CREDENTIALS`) are removed from the command's environment; the bundled scripts read their keys from the configuration (`SecretReferences.config_value`). User scripts in the shared folder's `scripts` run only in the Python container.
- **Custom apps and helpers** (`apps/`, `helpers/`): loaded through `SharedPathGuard.user_code_files` and `code_files`, which load nothing from a folder that is a link, and no file that is a link, has another hard link, or really lies outside its folder. The DSL loader loads an app's `_constants.rb` and `_tools.rb` under the same rule (`code_file?`).
- **Container definitions** (`services/`, `apps/*/services/`): `monadic.sh` includes their `compose.yml` in every `docker compose` run and builds them with "Build User Containers". The generated include file is written to `~/monadic/config`, not the shared folder.
- **Other files the host reads or writes in the shared folder:** the Electron app writes the Document DB export and its decrypted import to a new file in `~/monadic/.staging` (beside the shared folder, mounted by no container) and renames it into place only when it was written and closed without an error (a rename replaces a link or FIFO instead of following it). It reads only the regular file it checked, without blocking (`app/no_follow_files.js`). Once in place, a file is in the shared folder like any other: what `import_db` then reads from there can still be changed before it does. It opens only the shared folder itself; any other folder is shown in its parent, since a folder there can be an app (`Name.app` on macOS) that opening would run.
- **The Python container's PATH:** the user's `scripts/` comes last, after the system's, so a `python3` or `bash` placed there does not replace the real one.

## Where the boundary is enforced

- **Containers (the desktop app):** `apps/`, `helpers/` and `services/` are mounted read-only over the shared folder in every container that mounts it: Python, Selenium and Extractor, and the Ruby container too (it only reads them). A write that reaches them through these mounts, by any path (a link, a race between a check and the write), is refused by the file system, and a new hard link into them cannot be made (a link across mounts, or into a read-only one, is refused). A file that already had a hard link elsewhere before the mounts is still writable through that other name. The server does not load a file with more than one link (`SharedPathGuard.code_file?`), but that does not cover a name written through and then removed before the next start: such old links can only be found by looking at the folders (see the release notes) or by moving the code out of the shared folder. `monadic.sh` (`ensure_code_dirs`) creates the three folders as the user before any container starts, and does not start when one cannot be created or is a link (taking containers down still works, as a way to recover).
- **Writes by the server into the shared folder:** the writes whose file name a model or a page chooses (the file tools, uploads, web search saves, files a provider sends, app templates, and AutoForge's project files) go through `SharedPathGuard.write_file!`, which refuses the `apps`, `helpers`, `scripts` and `services` folders (by name, without case, and where they really are), refuses a link in the file's place (before and after resolving), and opens with `File::NOFOLLOW`. Writes whose names the server makes (generated images, audio, transcripts) and AutoForge's patch application and restores do not; in the containers the read-only mounts cover them. This is a second line in the containers and the only one on the host.

## Development mode

With `rake server:debug` the server runs on the host. The other containers still mount `apps/` and `helpers/` read-only, so code a model runs cannot write there directly, nor make a new hard link into them. The server on the host, though, follows the paths it is given: `write_file!` refuses a link in the file's place, but a parent folder replaced by a link between the check and the open still leads elsewhere (`File::NOFOLLOW` covers the last part of the path only).

So in development mode the server loads no custom apps or helpers from the shared folder (`SharedPathGuard.user_code_files`) unless it is started with `MONADIC_LOAD_USER_CODE=true` in the shell:

```bash
MONADIC_LOAD_USER_CODE=true rake server:debug
```

Only the shell can turn it on. `rake server:debug` reads `~/monadic/config/env` into `ENV` before it starts the server, and passes the setting on only when the shell had it. The server also ignores it whenever that file mentions the name anywhere (its bytes are searched, never parsed or shown; the file under the account's home and under `HOME`), since Dotenv accepts forms a line parser would miss (`NAME: value`, a BOM, CR line ends). Whether the server runs in a container is taken from `/.dockerenv`, not from `IN_CONTAINER`. When it is off and the folders hold files, the server says so once at startup. Set it only while you work on a custom app, and not while the model reads untrusted documents or pages.
